# 开发工作台 · 竞品调研与需求缺口分析

> 编制：缪胜
> 日期：2026-09-28
> 依据：需求摘要 v1.0（已冻结）+ 市面同类产品调研（2026-09 时点）
> 结论先行：你的定位（规划侧提示词工程）在市面属差异化生态位，方向成立；但有 4 个 P0/P1 级缺口建议补入需求，5 个 P2 级建议纳入规划。

---

## 一、市面同类产品格局

### 关键发现：市场分「执行侧」与「规划侧」，你做的是后者

| 阵营 | 代表产品 | 核心逻辑 | 与你的关系 |
|------|----------|----------|-----------|
| **执行侧**（主流红海） | GitHub Copilot Agent、Cursor、Devin、Claude Code、通义灵码、Trae、CodeBuddy、文心快码 | AI 直接生成/修改代码，绑定自家 IDE 或仓库 | 你的提示词的**下游消费者**，不是竞品 |
| **规划侧**（接近你的定位） | MetaGPT（多角色流水线：PRD→设计→API→代码→Review）、文心快码 SPEC 白盒流（需求→任务→代码→预览，每步人工校验） | 结构化拆解 + 每步人工确认 | **理念最接近**，但它们最终自己写代码，你在"提示词"处交棒 |
| **提示词编排/治理** | PromptLayer、LangSmith、Dify | 提示词版本化、评估、观测 | 它们的**治理能力**是你缺的（见缺口） |
| **多智能体编排框架** | LangGraph、CrewAI、AutoGen | 状态图、角色协作、断点恢复 | 你的技术实现可借鉴（LangGraph 的 checkpoint 机制 ≈ 你的断点续跑） |

### 对你有利的市场信号
- DORA 2025 报告：AI 提效的前提是**更强的评审纪律**——你"每步产出需确认"的设计正好命中
- 上下文窗口仍是硬约束，"按上下文上限拆任务"是真实痛点，市面无产品把它做成一等公民
- 文心快码 SPEC 流验证了"白盒、每步可校验"的路线有市场需求

## 二、需求缺口清单（按优先级）

### P0 —— 强烈建议补入（不做会明显削弱产品完整性）

| 编号 | 缺口 | 现状 | 市面对标 | 建议补法 |
|------|------|------|----------|----------|
| G1 | **提示词版本管理与回滚** | F6 只有"归档"，无版本概念 | PromptLayer 核心能力：提示词/流程/工具整体版本化，可回滚对比 | 提示词迭代修改时保留历史版本，支持版本对比与回退到任意版本 |
| G2 | **任务依赖与执行顺序** | 任务拆分了，但没提任务间依赖 | LangGraph DAG、GitHub agent 的 implementation plan 都显式建模依赖 | 拆分结果输出为带依赖顺序的任务清单（如 DAG 或编号序），标明"哪些可并行、哪些必须先后" |
| G3 | **工程规则/编码规范上下文层** | C9 只有"手动选择上下文文档" | .cursorrules / CLAUDE.md / AGENTS.md 模式：仓库级规则文件已成行业标准 | 项目级持久"工程规则"配置（技术栈约定/编码规范/目录约定），生成每个提示词时自动注入，无需每次手动勾选 |
| G4 | **提示词交付前的人工预览与微调** | F3 流程里生成即交付 | 市面共识：human review 必不可少；你的 F1 有评审师，F3 却没有对应环节 | 每条提示词生成后先进入预览态，可人工编辑微调后再"定稿归档" |

### P1 —— 建议补入（影响日常使用体验）

| 编号 | 缺口 | 现状 | 市面对标 | 建议补法 |
|------|------|------|----------|----------|
| G5 | **执行状态跟踪（提示词之后）** | 无 | Augment Tasklist、GitHub agent 的 PR 状态 | 任务清单上可手动标记"已投喂/已完成/失败"，形成项目进度看板（不自动感知外部 IDE，人工标记即可） |
| G6 | **提示词效果反馈记录** | 无 | PromptLayer evals（轻量版） | 每条提示词可记录一行"执行结果备注"（成功/失败/返工原因），为迭代提供依据 |
| G7 | **敏感信息脱敏提醒** | 无 | OWASP Agentic Top 10（工具滥用/秘钥泄露） | 生成/导出提示词时扫描疑似秘钥、密码、内网地址，提示用户脱敏后再投喂外部 AI |

### P2 —— 纳入规划即可（二期考虑）

| 编号 | 缺口 | 说明 |
|------|------|------|
| G8 | Token 用量与成本统计 | Provider 层已可采，加个用量报表即可，一期可不做 |
| G9 | 组织级模板知识库 | 跨项目复用优秀提示词模板/项目模板，一期先项目级 |
| G10 | Git 深度集成 | 归档目录自动 commit/branch；一期靠"Git 友好"的文件存储即可 |
| G11 | 回归提示词的差异感知 | 「回归」模块读取上次任务清单自动圈定回归范围（一期人工指定） |
| G12 | 多人并发编辑冲突处理 | 无鉴权前提下矛盾，等权限体系一起做 |

### 明确不建议做的（守住边界）
- ❌ 内置代码执行/IDE 能力 —— 市面红海，且违背你的 C1 分工边界
- ❌ 自动感知外部 IDE 执行结果 —— 深度集成成本极高，人工标记（G5）已够用

## 三、修订建议汇总

若你认可，需求摘要变更如下：
- **新增功能**：G1 提示词版本管理、G2 任务依赖编排、G4 提示词预览微调、G5 执行状态跟踪、G6 效果反馈记录、G7 敏感信息提醒（并入 F3/F6 描述）
- **新增约束**：G3 工程规则上下文层（并入 C9 升级：手动选文档 + 持久工程规则自动注入）
- **P2 项**写入 SRS「后续规划」章节，不进一期范围
