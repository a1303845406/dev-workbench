## 2 POC-1：codegraph 结构画像选型与性能实测（G-01 / CON-11）

### 2.1 待验证问题

| 编号 | 问题 |
|------|------|
| Q1 | 万级文件项目上生成结构画像的耗时/内存/产物大小是否满足"常规操作秒级~十秒级"体验 |
| Q2 | AOCI-CODE 的符号+语义双层索引（含数据库 schema）对"目录健康度 + 依赖摘要"画像的支撑度，是否可省去自研 |
| Q3 | 集成形态成本：外部进程调用（subprocess + FRAS 文本解析）vs 进程内库（tree-sitter 绑定）的工程复杂度 |
| Q4 | 增量维护能力：二次扫描是否显著快于全量（影响续扫与反复扫描体验） |
| Q5 | AOCI-CODE license（NOASSERTION）是否允许本项目使用方式 |

### 2.2 基准环境与样本集（G-09）

- 环境：一台开发主机（Windows 11 + Python 3.12），记录 CPU/内存/磁盘型号；同一主机跑两候选；
- 样本三档（各备一份，禁用业务敏感仓库）：
  - S 小型：≤500 文件（如本项目文档库）；
  - M 中型：2000~5000 文件的典型 Web 项目（开源仓库脱敏后可用）；
  - L 大型：≥10000 文件的单体仓库。

### 2.3 测量项与记录表

| 指标 | 口径 | 记录 |
|------|------|------|
| 全量画像耗时 | 冷/热缓存各 3 次取中位 | s |
| 增量耗时 | 改动 ≤50 文件后二次扫描 | s |
| 峰值内存 | 进程监控 | MB |
| 产物大小 | 索引/画像文本 | MB；Git 友好性（diff 噪声）主观评估 |
| 画像支撑度 | 语言构成/目录健康度/依赖摘要三项的可用性评分 | 0-2 分/项 |
| 集成工作量 | 封装代码行数与异常场景数 | 人日估算 |

### 2.4 判定准则（阈值草案，实测后冻结为 AC-03 验收值）

| 档位 | 全量耗时建议上限 | 说明 |
|------|------------------|------|
| S | ≤ 5 s | 常规操作秒级（NFR-02） |
| M | ≤ 30 s | 异步作业 + 进度条 |
| L | ≤ 120 s | 异步 + 续扫；超限则默认深度降档 |

- **选型规则**：AOCI-CODE 满足阈值 + 画像支撑度 ≥5/6 + license 结论为"允许"（含商用/内部工具用途）→ 选 AOCI-CODE，tree-sitter 转二期 FU-03 候选；任一不满足 → 自研 tree-sitter（仅符号层，语义层不做承诺）；
- license 结论歧义时：按"并行使用"模式采用（用户在外部自建索引、产物经手动选择入上下文，CON-13），产品不内置其调用。

### 2.5 步骤与时间盒

1. license 确认（0.5 人日）：读取仓库 LICENSE/README；必要时向作者提问；结论记录四选一：允许/禁止/允许但有限制（列明）/不明确（按并行使用模式）；
2. AOCI-CODE 跑通三档样本（1 人日）：记录 2.3 全部指标；
3. tree-sitter 最小实现（1.5 人日）：仅语言构成 + 符号计数 + import 关系；
4. 对比报告与选型结论（0.5 人日）。

**退路**：两候选均不达标 → FR-03 一期降级为"纯统计画像"（语言构成/目录规模/依赖清单，无符号层），AC-03 阈值按实测重新协商（变更流程）。

## 3 POC-2：上下文预算测算口径验证（G-02）

### 3.1 待验证问题

| 编号 | 问题 |
|------|------|
| Q1 | `token ≈ chars/4` 经验公式在中英混合提示词上的偏差区间 |
| Q2 | 系数 0.6 拆分出的任务单元投喂外部 IDE 是否可独立执行（AC-04 补充抽样实测口径） |
| Q3 | 输出预留：单环输出 + 交接摘要占用是否需要在输入预算中显式扣除 |

### 3.2 方法

1. 语料：构造 30 条代表性输入包（四层比例仿真：角色 15%/全局 20%/任务 25%/上游 40%），中英比例 7:3；
2. 用目标模型 tokenizer（或 tiktoken 近似）实测 token 数，比对 `chars/4` 与 `chars/系数` 拟合，给出建议估算函数与安全裕度；
3. 投喂实测：按拆分算法对 1 个样本项目（中型）产出任务清单，**抽取 ≥2 个任务单元**原样投喂外部 IDE（Trae/Cursor 任一），记录：是否需要补充上下文、是否一次执行成功、返工原因归类（AC-04 抽样实测同口径）；
4. 结论回写：冻结 `coefficient` 默认值与估算函数（ADR-8），必要时调整拆分算法的输出预留比。

### 3.3 判定准则（草案）

- 估算偏差 ≤ ±15%（置信 90%）→ 采用字符估算法；超限 → 内置轻量 tokenizer 计数（引入依赖需评审）；
- 投喂实测 2/2 可独立执行 → 0.6 系数冻结；出现需回补上下文的情形 → 系数下调至 0.5 或拆分粒度收紧，重测一轮。

时间盒：2 人日（含实测等待）。

## 4 POC-3：关键词级规范冲突检测可行性（2.9.3 [需技术团队确认]）

### 4.1 待验证问题

Q：对 rules.md 中的"放宽性表述"，关键词命中法的查准率/查全率是否达到"告警有用、不构成干扰"的水平（建议线：查准 ≥0.7、查全 ≥0.6；未达线 → 降级为"仅文档声明不做检测"或扩充为句式约束）。

### 4.2 方法

1. 正样本 ≥20 条：放宽表述及变体（"允许硬编码""密钥可写入配置文件""异常可以不处理""测试可跳过""无需写注释""可以顺手重构"等口语化改写）；
2. 负样本 ≥30 条：正常项目规则（"禁止硬编码""统一异常处理""测试覆盖率要求"等，含与关键词字面相近但不放宽的句子，如"禁止允许硬编码的配置项"）；
3. 用 constraints-package.md 初始 `conflict_keywords` 跑匹配，统计 P/R；误报样本归因 → 调整关键词/补充否定前置规则（"禁止|不得 + 关键词"不计命中）；
4. 结论三选一回写 04 文档 §7.3：可用（含修订后的关键词集）/ 需句式约束（给出约束模板）/ 一期不做自动检测（依赖人工把关，SRS 口径允许）。

时间盒：1 人日。

## 6 风险与退路汇总

| 风险 | 退路 |
|------|------|
| AOCI license 不明确/不允许 | 并行使用模式（用户侧自建索引）；或自研 tree-sitter |
| 万级目录性能不达标 | 深度降档 + 截断 + 续扫；纯统计画像降级 |
| 中转站 tokenizer 差异大 | 按用户所配 Provider 主模型逐一校准（配置项 per-provider 估算系数） |
| 投喂实测依赖外部 IDE 环境 | 以手动粘贴方式执行，不强求自动化 |
