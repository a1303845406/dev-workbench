## 1 FR-01 七阶段流水线引擎

### 1.1 状态机

```
(创建) → S1 → S2 → S3 → S4 → [S5] → S6 → S7 → (完成)
         └──────── 每阶段内部：draft ⇄ (修订) → confirmed(推进门) ────────┘
```

- 阶段状态：`not_started / draft / confirmed / skipped`（仅 S5 可 skipped，且必须用户显式确认跳过，FR-01 规则 1）；
- 转移唯一入口：确认接口（03 文档 §3.3）；confirmed 后阶段只读，修订须走"退回重开"（S7 之后不允许退回 S5 前，保证冻结语义）；
- S5 两段冻结：单阶段内部分两步确认（`frozen_business` → `frozen_scope`），状态文件记录两个时间戳。

### 1.2 各阶段角色与调用装配（无状态逐轮，FR-01 规则 8）

| 阶段 | 角色模板 | 额外指令段（拼入角色层） |
|------|----------|--------------------------|
| S1 | requirement-guide | 5W1H 框架；先开放后收敛；输出须含"模糊点标注清单"（`[模糊: …]` 行内标记） |
| S2 | requirement-analyst | 强制 B/F/N/C 四类表格输出；去重合并说明；缺口清单（P0~P3） |
| S3 | requirement-analyst | 每轮 ≤3 问；选择题优先（给出选项 A/B/C）；示例驱动；按优先级排序 |
| S4 | requirement-analyst + 自审段 | 先输出三角度自审（有门无路/迭代对称性/旅程断点，逐条结论）再请求确认（AC-01 可见自审记录） |
| S5 | 冻结主持 | 两段冻结清单逐项宣读；变更须走变更流程的提示语 |
| S6 | requirement-writer | SRS 规范骨架；编号追溯链（B→F→FR，功能清单含"来源"列）；条目可选 EARS（WHEN…THE SYSTEM SHALL…）；配图以 .drawio 占位引用 |
| S7 | requirement-reviewer | 三维度（可落地性/合理性/应用前景）独立审核；输出分级问题清单（严重/一般/建议），问题编号 `Q-<级别>-<序>`；不代写修订 |

**输入组装**（每轮）：

```
system = 角色层(阶段角色模板 + 额外指令段)
user   = 状态层(滚动底稿全文快照) + "\n\n---\n本轮用户输入：\n" + user_input
```

- 角色层与额外指令段来自 `configs/modules/`（可配置，NFR-07）；
- 快照即底稿落盘时的原文，同时写入本轮阶段记录文件（AC-15 还原依据）；
- 不传任何会话历史——历史语义全部在底稿的"轮次记录"区。

### 1.3 底稿读写协议

1. 引擎为六区**区识别**维护固定标题正则（`## 一、项目语境` … `## 六、实现形态细化`）；
2. 每轮对话后：模型输出的 `draft_update` 按 JSON 补丁（`{section, action: append|replace, content}`）应用到底稿；解析失败则原文追加至"轮次记录"区并人工提示；
3. 用户手改底稿合法（人类可读可改）：下一轮组装前重新读盘，以文件为准；
4. 整文件原子替换写回；头注（当前阶段/时间）同步刷新。

### 1.4 推进门事务（AC-01）

```
confirm(stage):
  1 读取该阶段最新 draft 产出 → 渲染确认预览
  2 用户提交 confirm(comment)
  3 写 阶段记录/S<n>-<名>-<seq>.md  (status: confirmed, 含用户意见)   ← 原子写
  4 更新底稿头注与对应分区
  5 更新 state/index.json（stage = next）
  6 写审计日志
  任一步失败 → 全部回滚（删除半成品、保持原 stage），返回错误
```

### 1.5 S7 修订协议（铁律落地）

1. 评审师输出问题清单（编号 `Q-S-01` 严重 / `Q-G-01` 一般 / `Q-B-01` 建议）；
2. 严重问题逐条请用户裁决（采纳/驳回/改判），形成裁决记录后修订才动笔；
3. 修订处在 S6 文档中内联标注 `【依据 Q-S-01 修订：…】`；
4. 修订完成后引擎执行**编号复核**：逐编号检索文档，未出现修订标注的严重问题阻断定稿并列出（AC-01"按编号复核无遗漏"）。

### 1.6 异常处理

- Provider 失败：保留当前 draft 与轮次序号，提示重试/切换 Provider（重试不增加 round 编号，失败轮记 `rounds[].failed=true`）；
- 底稿损坏（六区结构缺失）：从 `阶段记录/` 最近 confirmed 阶段重放重建 + `.bak` 滚动副本兜底，提示回退位置；
- 用户中途退出：无服务端会话可丢——重新打开项目时从 state/index 列出未完结流水线（P1 恢复入口同机制）。

## 2 FR-04 编排器（Orchestrator）

### 2.1 组件与数据流

```
tasks.json ──→ 计划生成器 ──→ plan.json（预览/人工调序/确认）
                                  │ confirm
                                  ▼
                       环执行循环（拓扑序 + 并行组）
             ┌────────────────────────────────────────┐
             │ 组装输入包(四层) → 预算校验 → Provider 调用 │
             │   → 解析正文+交接摘要 → 全量落盘 → 推进      │
             └────────────────────────────────────────┘
```

### 2.2 计划生成（9.e）

1. 读 tasks.json 的 `depends_on` → 拓扑排序（Kahn）；同层任务分入同一 `parallel_group`（组内并发默认 2，可配）；
2. 每任务按 `modules_selected` 顺序展开为环（任务×模块）；环间依赖 = 任务依赖 + 模块顺序（同任务内第 i 环依赖第 i-1 环）；
3. 输出 plan.json（drafting），前端渲染可拖拽调序；`PUT /plan` 校验：调序不得违反任务依赖（同任务环顺序可调，跨任务依赖环不可前移）。

### 2.3 环执行循环（伪代码）

```python
async def run_plan(plan):
    while ring := next_ready_ring(plan):        # 拓扑序取依赖满足的环
        async in parallel_group(ring):          # 组内并发（默认 2）
            for attempt in 1..max_retries+1:    # 默认 3 次重试，可配
                inp = assemble_input(ring)      # 四层（§2.4）
                check = budget_check(inp, ring) # §2.5：超限→压缩上游层→仍超→阻断
                if check.blocked: suspend(ring, BUDGET_EXCEEDED_BLOCKED); break
                confirm_outbound(inp)           # G-10：确认记录 + meta.confirmed_at
                try:
                    result = await provider.chat(to_messages(inp), stream_cb=sse(ring))
                except RetryableError:
                    record_failure(ring, attempt); continue
                except FatalError as e:
                    suspend(ring, e.code); break
                out = parse_output(result.text)     # 正文 + handoff（§2.6 协议）
                persist_ring(ring, inp, out)        # input.md/output.md/handoff.md/meta.json
                mark_done(ring); emit("ring.completed"); break
            else:
                suspend(ring, RING_RETRY_EXHAUSTED)  # 挂起，等人工恢复（FR-06）
    finalize_tasks(plan)   # 全环完成 → 任务单元完结 → 看板待投喂
```

- 执行中每环落盘后自动推进（9.e）；服务重启后：plan.status=running 且存在未完成环 → 置 suspended（文件权威态），入口提示恢复。

### 2.4 输入包四层组装（9.c）

```
input.md 结构（亦是 messages 组装依据）：
<!-- layer:role -->      该模块角色系统提示词（modules/<module>.md 正文）
<!-- layer:global -->    硬约束包（constraints-package.md，含 package_version 头注）
                         + "\n\n" + rules.md 全文                       ← 顺序固定（2.9.3-1）
<!-- layer:task -->      任务描述/验收标准/复杂度档位/关联需求条目(EARS)/外发范围说明
<!-- layer:upstream -->  直接依赖环的 handoff.md 全文（取最新定稿版本，§2.6）
                         + 路径引用清单（"执行时读取 <workspace 相对路径>"）
```

- 非直接依赖但需引用的产出只以**项目内文件路径引用**带入（9.d）；
- 组装后四层字符量分节统计进 meta（预算审查可视化）。

### 2.5 预算测算与校验（G-02 / 9.f）

1. 口径：`任务预算 = 声明上下文上限 × coefficient(默认 0.6，complexity-map 可配)`；
2. 单位统一为 tokens：记录字符数用于初估与展示；以目标模型 tokenizer 复核输入 tokens，并预留输出和协议开销。不得将字符数与 token 数直接取最大值比较。`chars / 4` 仅为 POC 待检验假设，不是中英文通用换算率；未知 tokenizer 时采用经 POC 校准的保守估计并标注不确定性。还须分别校验生成 Provider 与外部 IDE 的窗口，两者不可混用；
3. 超限处理序：压缩上游层（handoff 截断为路径引用并告警）→ 复查 → 仍超则阻断该环并提示拆分上游任务（`BUDGET_EXCEEDED_BLOCKED`）；
4. 拆分期（§3.4 split）同样以该口径预估单任务 est_chars，超预算任务在拆分阶段即递归再拆。

### 2.6 交接摘要协议与定稿联动（9.d / AC-16）

1. 生成：角色层模板统一附加指令——"正文之后输出一行分隔符 `===HANDOFF===`，其后输出 ≤{handoff_limit_chars} 字符的交接摘要（本环做了什么/关键决策/接口与数据约定/遗留风险）"；
2. 解析失败：记录 `handoff_invalid` 并阻断依赖环，提供重新生成或人工修订入口；不得截取正文尾部冒充语义完整的交接摘要。每次尝试独立留档；
3. 定稿联动：
   - handoff.md front matter 记 `based_on_version`（产出对应的提示词版本）；
   - 用户微调定稿（version+1）后，服务端比对 `based_on_version ≠ 最新 final 版本` → 置 stale，SSE `handoff.stale` + 定稿响应携带 `handoff_stale`；
   - `regen-handoff` = 以定稿正文为任务层补充、仅重新生成摘要的轻量调用（复用同输入包、正文不重算）；
   - 下游组装**永远取最新 final 版本对应的 handoff**；stale 未处理时下游环启动前阻断并提示（保证 AC-16 语义）。

### 2.7 复现与审计（9.g）

- 任意环可 replay：`input.md` 即完整输入，`meta.json` 含 provider/model/温度/预算参数——重放 = 同输入重发（结果可能不同，但输入可证）；
- 审计视图（资产库）按 任务 → 环 → 调用 三级展示，命中 AC-14③"完整可查"。

## 3 FR-05 测试用例机制

1. 测试环角色模板（modules/test.md）固定产出结构：`TC-F-*`（功能）/`TC-B-*`（业务）必出；`TC-P-*`（性能）仅当任务层声明 `performance: true` 时产出——模板指令 + 落盘校验双保险（未勾选时解析后过滤并告警，AC-05）；
2. 每条用例头部标注 `覆盖: <FR/任务编号>`；解析器校验编号存在于 tasks.json.req_refs / 需求文档追溯链，失败项列出供人工确认；
3. 回归模块独立：modules/regression.md 产回归提示词（人工指定回归范围，一期无差异感知——G11 二期）；
4. 不满足覆盖要求时"重生成"= 新版本用例集文件，旧版保留（FR-05 异常处理）。

## 4 FR-03 扫描器

### 4.1 扫描管线

```
校验(存在性/读权限/白名单 realpath 前缀) → 遍历(迭代栈; 不跟随符号链接; 深度≤12; 条数≤20000)
  → 统计(语言构成/目录规模/文件分布/依赖清单提取: package.json/requirements.txt/pyproject/pom.xml/…)
  → codegraph 适配层 structure_summary()（失败→降级纯统计并标注）
  → 目录健康度(与所选模板 dirs 清单对照) → 结构画像.md + 规整建议.md + 扫描摘要.json(resumable_token)
```

- 续扫：`resumable_token = {last_path, counters}`；中断后 resume 从 last_path 继续（FR-03 异常处理）；
- 超限：达到上限即停止并出部分报告（含"已截断"标注），用户可调上限重扫。

### 4.2 分级建议生成（FR-03 规则 3）

| 级别 | 判定示例 | 处理 |
|------|----------|------|
| 自动归位（低风险） | 散落根目录的 `.md` 文档 → 建议移入 `docs/`；测试文件不在 tests/ → 移入 | 生成整改方案与路径对照清单；不由服务端移动或修改源文件，交由人工或外部 IDE 执行（CON-01） |
| 需人工决策 | 疑似入口文件多套、构建配置冲突、超大目录、二进制混杂 | 仅列事实与风险，不出自动动作 |

建议均含"依据"列（命中规则 id / 健康度规则），报告可归档与导出（OpenSpec change 结构，FR-08）。

## 5 脱敏扫描引擎（FR-04 规则 7）

- 规则来自 sanitize-rules.json（02 文档 §6.5）：正则 + severity（block/confirm）；
- 触发点：复制到剪贴板前、导出生成前、（可选）定稿前预检；
- 命中呈现：逐条 `{rule_id, severity, excerpt(命中上下文 40 字符，命中段打码), position}`；block 级存在即 422 阻断；confirm 级逐项勾选"已脱敏/保留"后放行；
- 服务异常（规则装载失败）→ 视为 block 全部导出（宁可阻断不可放行）并告警。

## 7 分层编码规范注入与冲突检测（2.9 / AC-17）

1. 注入器：全局层 = `constraints-package.md（含版本头注）+ "\n\n" + rules.md`，顺序固定不可调；包版本随 gen_params 归档（FR-04 规则 10）；
2. 版本升级：包文件 `package_version` 变更 → 新生成提示词用新版本；既有提示词归档的版本不变（AC-17③）；
3. 冲突检测（一期关键词级，ADR-9）：
   - 时机：rules.md 保存（PATCH）时 + 提示词组装前（防御性）；
   - 算法：对包内 `conflict_keywords` 逐条在 rules.md 做不区分大小写匹配；命中 → 返回 `RULES_CONFLICT_WARNING`（422 + 命中行与关键词），**警示不阻断保存**（人工兜底，SRS 2.9.3-2）；
   - 已知局限（显式声明）：无法识别同义改写（"密钥可以直接写进配置"）；POC-3 用标注样本集测误报/漏报率，结论回写本文并决定是否调整关键词集或补充规则句式约束；
4. 可关闭性：包不可整体关闭；`overridable` 列表为空的初始集意味着无任何条目可豁免——注入器跳过"豁免"逻辑分支（预留字段仅作格式兼容）。

## 10 任务拆分预算算法（G-02 补充）

```
split(task):
  est = estimate_chars(task 描述+验收+关联需求条目+rules 摘要+上游 handoff 预留(500))
  if est ≤ budget: emit 单任务单元
  else: 按模块内职责切分（crud 边界/接口边界/数据模型边界启发式 + 模型建议）
        → 子任务继承 depends_on 关系并新增链内依赖 → 递归
输出：tasks.json（含每单元 budget_chars 与 est_chars），超限未拆尽 → 阻断并列明
```

> 启发式切分先由模型在 compose/split 调用中给出（含切分理由），引擎仅做预算校验与编号——保证可解释、可人工调整（G-08 半自动口径）。
