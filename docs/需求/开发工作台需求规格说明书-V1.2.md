## 1 引言

### 1.1 编写目的

本文档描述"开发工作台"（AI 辅助开发工作台）项目的业务需求、功能需求、非功能需求、接口需求、数据需求与验收标准，作为产品设计、开发、测试与验收的依据。

预期读者：项目经理、产品设计人员、开发团队、测试团队。

### 1.2 项目背景

随着大模型编程工具（外部 IDE Agent）的普及，开发团队的瓶颈正从"写代码"转移到"规划与喂料"：需求不清、任务拆分粒度失控、提示词质量参差、过程文档散乱。开发工作台定位于开发全流程的**规划侧**，覆盖"需求探索 → 目录规范 → 提示词工程 → 测试用例"链路，产出规范文档与可直接投喂外部 IDE 的提示词，帮助团队以可控、可追溯的方式驱动 AI 执行侧完成开发。

本项目由材智科技提出并实施。部署形态分期演进：一期单机 localhost 使用；二期演进为团队局域网共享访问（见 2.7 分期规划）。

|------|------|

## 2 总体描述

### 2.1 产品概述

开发工作台是一个 AI 辅助开发全流程规划侧的 Web 应用：一期以 localhost 单机模式运行（服务端与浏览器同机），二期演进为团队局域网共享访问。产品不直接生成或修改代码，而是通过四条能力链路产出开发资产：

1. **需求探索 Agent（FR-01）**：对齐专业需求分析团队 SOP 的七阶段流水线（引导对话→碎片提炼→澄清追问→摘要确认→范围冻结→文档编写→评审修订），引导用户将模糊想法沉淀为规范需求文档；
2. **目录结构治理（FR-02/FR-03）**：为新项目按模板一键生成规范目录骨架；对存量项目（同机路径）由服务端直接扫描分析并给出规整建议；
3. **提示词工程（FR-04/FR-05）**：以 10 模块动态组合引擎，按任务复杂度自动选择开发流程模块，按外部 IDE 上下文窗口上限拆分任务单元，逐模块生成提示词与测试用例，支持预览微调、版本管理与按项目归档；
4. **生态工具协同（FR-08）**：与主流 SDD 工具链、MCP 工具生态**并行使用**（非代码集成）——产物格式对齐导出、提示词内嵌工具使用指引、项目级协同工具注册表。

产品全部数据以 Markdown 与 .drawio 等文本格式存储于文件系统，天然兼容 Git 版本管理与团队协作。

### 2.2 产品功能概览

| 功能编号 | 功能名称 | 概述 | 优先级 |
|----------|----------|------|--------|
| FR-01 | 需求探索 Agent | 七阶段多角色流水线需求引导与文档生成，每步确认 | P0 |
| FR-02 | 新项目初始化 | 模板化一键生成规范目录骨架（含工程规则骨架） | P0 |
| FR-03 | 已有项目规整 | 服务端直读同机路径扫描分析与整改建议 | P0 |
| FR-04 | 提示词工程 | 动态模块组合、上下文预算任务拆分、提示词生成/预览/脱敏 | P0 |
| FR-05 | 测试用例生成 | 功能/业务必选、性能可选的测试用例与回归提示词 | P0 |
| FR-06 | 流水线持久化与断点续跑 | 每步实时存档（P0），中断恢复（P1） | P0/P1 |

### 2.3 用户特征与角色定义

| 角色 | 描述 | 权限 |
|------|------|------|
| 团队成员 | 具备基本软件开发协作能力的开发者 | 创建项目、运行流水线、生成/编辑/导出提示词、标记执行状态、配置协同工具。一期无账号体系、无权限区分（localhost 单机模式），数据模型预留多用户扩展（CON-03，预留方式见 6.2 S-06） |

### 2.4 运行环境

| 类别 | 要求 |
|------|------|
| 服务端 | 一台开发主机（Windows/Linux 均可），Python 3.12+ 运行时；与使用者浏览器同机（localhost 单机模式，P-01）；服务端对该机文件系统有读权限（FR-03 依赖） |
| 客户端 | 现代浏览器（Chrome/Edge/Firefox），经 `http://localhost:<port>` 访问（P-01：localhost 天然满足 Secure Context，Clipboard API 可用） |
| 网络 | 一期无需网络暴露（仅 localhost 回环）；**禁止直接以局域网 IP + HTTP 方式对外提供服务**——该形态下 Clipboard 等浏览器 API 因非安全上下文失效，属功能失效风险（P-01）。二期局域网共享部署时必须启用 HTTPS（自签/mkcert 证书 + 客户端证书信任分发方案），并先行实施 FU-02 门禁鉴权（见 2.7.2） |

### 2.5 设计约束

| 编号 | 约束 |
|------|------|
| CON-01 | 本工具不直接执行代码修改，产出提示词交由外部 IDE 执行或人工拷贝 |
| CON-02 | Web 应用，单点部署；**一期 localhost 单机模式**，二期演进为团队局域网共享访问（届时强制 HTTPS + 门禁鉴权，P-01，见 2.7 分期规划） |
| CON-03 | 一期无账号/权限体系，数据模型预留多用户扩展（预留落地方式：project.json 含 owner 字段，见 6.2，S-06） |
| CON-04 | 模型接入采用可配置 Provider 层：官方 API 与自建中转站均可接 |
| CON-05 | 目录模板内置默认模板 + 用户可自定义 |
| CON-06 | 一期 localhost 模式下 Clipboard 等 Secure Context API 天然可用（P-01），禁止局域网 IP+HTTP 部署形态；FR-03 已改为服务端直读，**不再依赖 File System Access API**，浏览器型号不构成主流程限制（V1.2） |
| CON-07 | 数据存储采用文件系统 + Markdown 文件，不引入数据库 |
| CON-08 | 后端 Python（FastAPI 方向）+ 前端 SPA |
| CON-09 | FR-01 产出 → FR-04 输入采用"手动选择上下文 + 项目级持久工程规则自动注入"；编码规范采用两层结构：产品内置通用硬约束包（项目层不可放宽）+ 项目级 rules.md 补充约束（见 2.9）；工程规则的新建/编辑入口由 FR-02（模板含 rules.md 骨架）与 FR-07（资产管理内编辑）承载（G-07） |
| CON-10 | 时间节点：里程碑与人力估算见 2.8 项目计划（G-04），细化排期在项目计划阶段确认 |
| CON-11 | 存量项目分析引入代码结构索引（codegraph 类，**服务端运行**）：选型候选包括自研 tree-sitter/LSP 解析与 **AOCI-CODE（符号+语义双层索引，含数据库 schema，Git 版本化纯文本产物，批次 0 POC 优先验证，V1.2.2）**：一期做 FR-03 结构画像；FR-04 相关代码切片注入列为二期 FU-03（见 2.7 分期规划）。原"全浏览器端运行（WASM）"要求随"源文件不出本机"约束移除而取消（V1.2）；性能阈值仍以批次 0 POC 实测冻结 |
| CON-12 | 项目统一采用 drawio 作为插图与流程图标准：过程文档图示及 FR-01/FR-04 产物图以 .drawio（XML 文本）为标准格式 |
| CON-13 | FR-08 生态工具协同遵循**并行使用原则**：只做产物格式对齐与使用指引嵌入，不做任何外部工具的代码级集成/API 依赖；外部工具不可用不得阻断本产品主流程（V1.2） |

| G11 | 回归提示词差异感知（自动圈定回归范围） | 二期；一期人工指定回归范围 |
| G12 | 多人并发编辑冲突处理 | 二期；与权限体系一并实施；一期仅轻量占用提示（S-04） |
| FU-03 | FR-04 相关代码切片注入（服务端 codegraph 圈定相关代码注入提示词上下文） | 二期候选；服务端选型（tree-sitter/LSP 类）在批次 0 POC 评估（CON-11 二期部分） |
| FU-04 | 项目删除回收站机制 | 二期；一期删除须二次确认并依赖备份恢复（6.3/S-01） |

#### 2.7.3 分期纪律

1. 二期项在一期开发中**不做实现**，但架构设计不得使其失去可能性（如 CON-03 的数据模型预留、Provider 层的用量采集点、S-05 日志来源字段为鉴权审计保留基线）；
2. FU-02 为硬性安全闸门：任何部署形态变更触及局域网共享或公网时，本条与 FU-05 自动升格为前置必做；
3. 新增需求一律先进入滚动底稿评审，确认后按本规章节归入相应期次并更新本表。

### 2.9 分层编码规范（V1.2.1 新增）

AI 编码规范采用**两层结构**，均自动注入提示词：

#### 2.9.1 第 1 层：通用硬约束包（产品内置）

产品内置一套针对 AI 编码失控点的底线规范，**所有项目的所有提示词默认注入，项目层不可放宽**。初始内容（以配置文件形式内置，可随产品版本演进，见 NFR-07）：

| 类别 | 硬约束（初始集） |
|------|------------------|
| 安全 | 禁止硬编码密钥/密码/令牌/连接串；不得在代码、注释、日志中残留敏感信息 |
| 依赖纪律 | 不得引入项目工程规则未约定的第三方依赖；确需引入时须显式说明理由并标记 |
| 改动边界 | 仅修改任务描述范围内的代码与文件；不得删除、重写或"顺手重构"范围外内容 |
| 质量底线 | 新增代码须带必要注释；不得静默吞异常（捕获后必须处理或显式抛出）；不留下未实现的占位逻辑且不声明为完成 |
| 输出纪律 | 不得编造不存在的 API/函数/配置项，不确定时显式声明"未验证"；严格按提示词要求的输出格式与文件路径产出 |

#### 2.9.2 第 2 层：项目补充约束（rules.md）

现有项目级工程规则承载技术栈约定、命名/目录规范、框架版本等定制内容，按项目编辑（CON-09）。

#### 2.9.3 分层规则

1. **注入顺序固定**：硬约束包在前、项目规则在后（后位提示对模型注意力更强，项目细节不被淹没）；
2. **收紧不放宽**：项目层只能附加或收紧约束，不得放宽系统层；一期实现关键词级冲突提示（如项目规则出现"允许硬编码"等表述时告警），完整语义冲突检测不做承诺 [需技术团队确认]，最终以人工把关兜底；
3. **版本化**：硬约束包带版本号，随生成参数归档（FR-04 规则 10），保证提示词可复现；
4. **可关闭性**：硬约束包不可整体关闭；单条约束是否允许项目级豁免，在包定义中以标记区分（初始集全部不可豁免）。

### 3.3 功能需求详细描述

#### 3.3.1 FR-01 需求探索 Agent（V1.2 七阶段重构）

- **功能描述**：内置多角色 Agent 流水线，工作法对齐专业需求分析团队 SOP，引导用户将模糊想法逐步澄清为规范需求文档。每一步产出必须经用户确认后方可进入下一步；架构师、测试师等角色以可插拔方式扩展。流水线共七个阶段：

| 阶段 | 承载角色 | 工作内容 | 产出物 |
|------|----------|----------|--------|
| S1 引导对话 | 需求师 | 5W1H 框架开放式提问（What/Who/Why/When/Where/How），先开放后收敛，完整记录原始表述并标注模糊点 | 原始表述记录（含标注） |
| S2 碎片提炼 | 需求师 | 将零散表述按 B 业务/F 功能/N 非功能/C 约束四类分类标注、去重合并、识别缺口 | 需求摘要初稿 + 缺口/模糊点清单 |
| S3 澄清追问 | 需求师 | 按优先级（P0 必须→P1 应该→P2 建议→P3 可选）收敛式提问：每轮 ≤3 问、选择题优于问答题、示例驱动 | 澄清记录（逐轮） |
| S4 摘要确认 | 需求师+用户 | 展示更新后的完整需求摘要，P0/P1 全部关闭后请用户确认 | 已确认需求摘要 |
| S5 范围冻结 | 用户 | 两段冻结：先业务需求冻结，再功能/非功能清单冻结；冻结后新增走变更流程 | 冻结记录 |
| S6 文档编写 | 需求师 | 按需求规格说明书规范编写完整文档；维护编号追溯链（B→F→FR，功能清单含来源列）；需求条目可选 EARS 记法表达（提升下游 AI 可读性）；配图以 .drawio 产出 | 需求规格说明书草稿 |
| S7 评审修订 | 评审师+用户 | 评审师从可落地性/合理性/应用前景三维度独立审核，输出分级问题清单（严重/一般/建议）；严重问题由用户裁决后修订，修订处内联标注问题编号，按编号复核无遗漏 | 审核报告 + 修订版文档 |

- **输入**：用户初始想法文本；过程中用户的确认意见与修改意见；可选的项目上下文文档。
- **输出**：各阶段产出物与最终需求规格说明书（Markdown）；配图以 .drawio 格式产出（CON-12）。
- **业务规则**：
  1. 阶段顺序默认 S1→S7，允许跳过 S5（小型任务可不做两段冻结）由用户显式选择；其余阶段不可跳过；
  2. 每步产出落盘保存后才允许推进；**该落盘机制属本需求的 P0 范围内置实现**（G-05），FR-06 的断点"恢复"为其 P1 读侧能力；
  3. **滚动工作底稿**：全程维护六区结构底稿（项目语境/原始表述/需求摘要滚动区/轮次记录/范围冻结区/实现形态细化），每阶段推进后即时更新，作为跨会话不丢信息的生命线（与 FR-06 状态存档同一文件体系）；
  4. **编号追溯链**：业务需求 B → 功能需求 F → 文档需求 FR 全程编号回链，功能清单保留"来源"列；
  5. **使用视角自审**：S4 确认前，需求师须从"有门无路（有能力是否有入口）、迭代对称性（有创建是否相应有归档/删除）、旅程断点（主流程是否中断无处可去）"三个角度自审并补充遗漏问题；
  6. 评审师（S7）独立输出审核报告，主理人角色只编排不代写；修订遵循"严重问题先裁决再动笔、修订处内联标注问题编号、修完按编号复核"铁律；
  7. 扩展角色（架构师/测试师等）可插拔，启用后在 S6 之后追加专项产出；
  8. **阶段对话编排（V1.2 增补，与 FR-04 规则 9 同构）**：S1-S3 等天然多轮对话阶段，每轮模型调用均为独立无状态调用，输入由三部分组装：①角色层（该阶段角色系统提示词）+②状态层（滚动底稿当前快照，规则 3）+③用户本轮输入。底稿即状态载体，任意轮次可复现、可断点恢复；每轮调用记录（输入+输出）随底稿体系落盘。
- **异常处理**：模型调用失败时保留当前阶段状态与已生成内容，提示重试或切换 Provider；用户中途退出不丢失任何已确认产出；底稿损坏时从最近完好版本恢复并提示回退位置。

#### 3.3.2 FR-02 新项目初始化

- **功能描述**：用户选择目录模板，系统在项目工作区内一键生成规范目录骨架及占位说明文件。
- **输入**：项目名称、所选模板（内置默认或用户自定义，CON-05）。
- **输出**：项目目录骨架（含 README、rules.md 工程规则骨架、docs/需求、docs/过程档案、src 等模板定义的结构）（G-07）。
- **业务规则**：
  1. 内置至少 1 套默认模板；模板以可编辑的目录清单文件描述；默认模板必须包含 rules.md 骨架（G-07）；
  2. 用户可将任意目录结构保存为自定义模板复用；
  3. 目标路径已存在同名目录时必须阻断并提示。
- **异常处理**：磁盘写入失败时回滚已创建条目并提示；模板文件损坏时提示修复或重置为默认模板。

#### 3.3.3 FR-03 已有项目规整（V1.2 改服务端直读）

- **功能描述**：用户提供项目所在路径（localhost 单机模式下即本机路径），系统由服务端直接扫描目录结构并进行分析，给出规整建议（可归位文件、缺失的规范目录、结构异常等），经用户确认后生成整改方案。
- **输入**：服务端可访问的项目路径（AS-04）；可选的扫描范围配置（深度/排除规则）。
- **输出**：项目结构画像（语言构成/目录健康度/依赖关系摘要）与规整建议报告（Markdown）。
- **业务规则**：
  1. 扫描由服务端直接读取文件系统完成（V1.2：原"源文件内容不出本机"硬约束与浏览器 File System Access API 依赖已移除；localhost 单机下服务端即用户本机，语义等价）；
| 2. 分析引擎结合服务端代码结构索引（codegraph 类，CON-11）生成结构摘要，压缩分析所需上下文；选型优先验证 AOCI-CODE（符号+语义双层索引，V1.2.2）；性能阈值以批次 0 POC 实测冻结（G-01）； |
  3. 建议区分"自动归位（低风险）"与"需人工决策"两级；
  4. **二期语义预警**：局域网化（FU-05）后"服务端路径"不再等价于"用户本机路径"，届时须重估本功能交互形态（恢复浏览器端授权扫描、或约定网络路径/挂载目录），写入 FU-05 实施清单（AS-04）。
- **异常处理**：路径不存在/无读权限时明确提示并校验；符号链接与循环目录做防穿越处理；超大目录扫描提供深度/条数上限并提示；扫描中断时保留已完成部分并支持续扫。

#### 3.3.4 FR-04 提示词工程

- **功能描述**：产品的核心引擎。基于用户选定的上下文（需求文档、项目文档）与项目级工程规则，自动选择开发流程模块组合，按外部 IDE 上下文窗口上限拆分任务单元，逐模块生成可直接投喂外部 IDE 的提示词。
- **输入**：用户手动勾选的项目内文档（需求文档等）；项目级工程规则（自动注入）；任务复杂度三档声明（简单/中等/复杂，G-08）与所处层面描述；上下文窗口上限参数；协同工具启用状态（FR-08）。
- **输出**：带依赖顺序的任务清单（DAG/编号序，标明可并行与先后关系）；**编排计划**（环执行序列，规则 9.e）；逐任务逐模块的提示词集合（含交接摘要，规则 9.d）；脱敏扫描报告；可选的 SDD 工具适配格式导出（FR-08）。
- **业务规则**：
  1. **模块池**：需求、概设、原型、详设、数据库设计、后端开发、前端开发、测试、回归、验收共 10 个模块；
  2. **自动组合（G-08）**：采用半自动模式——用户对任务做三档复杂度声明（简单/中等/复杂），agent 依据档位与任务层面给出模块组合建议，用户可干预调整；档位→模块组合的映射关系写入可配置文件（呼应 NFR-07），保证行为可复现、可测试；
  3. **硬约束**：任意组合必须包含 需求 → 任意开发类模块 → 测试 → 验收 最少四模块；
  4. **拆分预算（G-02）**：模块内任务单元以外部 IDE 上下文窗口上限为粒度预算，超预算任务必须继续拆分。预算测算口径：**任务预算 = 用户声明的模型上下文上限 × 保守系数（默认 0.6，可配置）**，按字符数估算、token 数复核；该口径 [需技术团队确认]，POC（批次 0）后冻结默认系数；**超预算必须拆分（V1.2.3）**：拆分可**多级递归**进行，直到每个叶子任务 ≤ 预算；仅承载分组、不直接执行的父任务为**容器任务**，执行、看板与环序列均以叶子任务为准；编排计划确认前存在超预算叶子任务即阻断并提示拆分（宁可阻断不可放行）；
  5. **工程规则注入**：项目级工程规则自动注入每个提示词，无需用户重复勾选（CON-09）；
  6. **预览微调与外发知情（G-10）**：每条提示词生成后进入预览态，支持人工编辑微调后定稿，未经定稿不可归档导出；预览界面显式展示外发范围（发送目标 Provider、包含的文档清单），用户确认后方可发起模型调用；**定稿联动（V1.2 增补）**：人工微调定稿后，该环原有的交接摘要基于修改前版本生成，系统须提示并提供一键按定稿内容重新生成摘要；下游环节输入包组装时永远取「最新定稿产出」对应的交接摘要；
  7. **脱敏扫描**：复制/导出前扫描疑似密钥、密码、内网地址，命中项提示用户脱敏确认（参考 OWASP Agentic 风险）；
  8. **工具指引嵌入（FR-08/CON-13）**：按协同工具注册表启用状态，在相关提示词中内嵌外部工具使用指引（如开发提示词附"use Context7 查询库文档"、改造类提示词附"用 Serena 符号检索定位"），指引为纯文本建议，不构成运行时依赖；
  9. **对话编排（V1.2 新增）——模型间多轮调用的规划机制**：
     a. **无状态逐环调用**：每个环节（某任务的某模块）= 一次**独立的、无会话状态的**模型调用。不采用连续多轮会话，原因：会话状态无法落盘（击穿 FR-06 断点续跑）、上下文自然膨胀（击穿预算控制）、会话不可复现（击穿归档审计）；
     b. **编排器（Orchestrator）**：服务端组件，按任务 DAG 拓扑序遍历任务单元（依赖未完成则等待，无依赖关系的任务可并行发起）；对每个任务单元按所选模块组合顺序**逐环执行**（如 需求环→详设环→开发环→测试环→验收环），并为每一环组装完整输入包；
     c. **输入包四层结构**（每环独立组装，四层总字符量计入该环预算校验）：
        - ① 角色层：该模块的角色系统提示词（模块池预置，可配置）；
        - ② 全局层：通用硬约束包（2.9 第 1 层，版本化）+ 工程规则 rules.md 全文（自动注入，CON-09，2.9 第 2 层）；
        - ③ 任务层：任务描述、验收标准、复杂度档位、关联需求条目（EARS 表达）；
        - ④ 上游层：**直接依赖任务的交接摘要**（见 d），非上游全文；
     d. **交接摘要（Handoff Note）**：每环完成时，除产出正文外，模型须额外生成一段面向下游环节的浓缩摘要（本环做了什么/关键决策/接口与数据约定/遗留风险，长度上限可配置，默认 ≤500 字符/环，预估值）。下游环仅携带直接依赖的交接摘要；非直接依赖但需引用的产出，以**项目内文件路径引用**方式带入（生成提示词中标注"执行时读取该文件"）；
     e. **编排计划先行**：环执行序列与依赖关系在任务拆分完成后即生成**编排计划**（可预览、可人工调整顺序），经用户确认后开始逐环执行；执行中每环结果落盘后**自动推进**下一环——V1.2.3 明确：落盘即推进，环级"定稿"不阻断下一环执行，定稿仅约束归档导出（规则 6）与下游摘要取材（AC-16：下游环执行时若上游交接摘要过期 HANDOFF_STALE，须先按最新定稿重生成摘要）；任一环失败则挂起于该环（结合 FR-06 断点续跑恢复）；
     f. **预算联动**：输入包组装后做预算校验，超预算时优先压缩上游层（截断为路径引用）并告警，仍超则阻断并提示拆分上游任务；
     g. 每次调用的完整输入包与输出**全量落盘**（6.1 编排目录），保证任意环节可复现、可审计。
  10. 提示词模板版本与生成参数一并归档，保证可复现。
- **异常处理**：模型输出超预算未拆分时自动触发拆分（可多级递归，直到叶子任务 ≤ 预算，V1.2.3）；模块组合不满足硬约束时阻断生成并说明缺失模块；脱敏扫描服务异常时阻断导出并提示（宁可阻断不可放行）；编排执行中单环连续失败（默认 3 次，可配置）时挂起任务单元并提示人工介入。

#### 3.3.5 FR-05 测试用例生成

- **功能描述**：由提示词工程的「测试」模块承载，为任务单元生成测试用例；「回归」模块独立生成回归测试提示词。
- **输入**：任务单元及其关联的需求条目、设计产物。
- **输出**：测试用例集（Markdown，含前置条件/步骤/预期结果）；回归测试提示词。
- **业务规则**：
  1. 测试用例必须覆盖**功能测试**与**业务测试**两类；
  2. **性能测试**为可选项，用户显式选择后生成；
  3. 每条用例标注其覆盖的需求/任务编号，保证可追溯。
- **异常处理**：需求条目缺失时提示先补全关联需求再生成；生成结果不满足覆盖要求时支持重生成并保留历史版本。

#### 3.3.6 FR-06 流水线持久化与断点续跑

- **功能描述**：所有流水线（FR-01 需求探索、FR-04 提示词工程）的每一步产出与状态实时落盘（P0）；用户中途关闭浏览器后，重新打开可从最近已确认步骤恢复继续（P1，G-05）。
- **输入**：流水线运行时状态（当前角色/阶段、已确认产出、待确认草稿）。
- **输出**：项目目录内结构化的状态存档（Markdown + 状态索引文件）。
- **业务规则**：
  1. 产出确认动作与落盘动作原子完成，先落盘后推进（本条为 P0）；
  2. 恢复时列出项目内所有未完结流水线及断点位置（本条为 P1）；
  3. 状态存档为人类可读文本，便于 Git 协作与差异审阅；FR-01 滚动底稿（3.3.1 规则 3）复用本存档体系。
- **异常处理**：写入失败时阻断推进并保留内存态供重试；存档损坏时从最近完好存档恢复并明确提示回退位置。

#### 3.3.7 FR-07 项目与提示词库管理

- **功能描述**：以项目为单位归档全部资产（需求文档、任务拆分、各模块提示词、测试用例、结构画像与规整报告），并提供版本管理、执行状态跟踪、效果反馈与工程规则维护能力。
- **输入**：各功能产出物；用户的状态标记与反馈备注；工程规则编辑内容（G-07）。
- **输出**：项目资产库（文件系统 Markdown/.drawio 组织）；提示词版本历史；项目进度看板。
- **业务规则**：
  1. 提示词每次修改保留历史版本，支持任意两版差异对比与回滚（G1）；
  2. 任务清单支持手动标记执行状态：待投喂/已投喂/已完成/失败（G5），形成看板视图；
  3. 每条提示词可记录一行执行结果备注（成功/失败/返工原因）（G6）；
  4. 归档结构 Git 友好，无锁定格式（CON-07）；
  5. **工程规则维护（G-07）**：工程规则（rules.md）的新建与编辑属于本需求功能，提供编辑入口；FR-02 模板生成的骨架作为初始内容；
  6. **删除保护（S-01）**：删除项目须二次确认（输入项目名确认后执行）；
  7. **占用提示（S-04）**：流水线运行中标记项目占用态；检测到他人/其他窗口同时编辑时给出警告（完整冲突处理见二期 G12）。
  8. **看板失败动态调整（V1.2.3）**：任务标记为失败时提供两种闭环动作——①**重新拆分**：按失败原因将失败叶子任务细化为子任务，子任务进入待投喂，原任务留档并标注"已细化拆分"及子任务关联；②**调整范围后重试**：记录调整说明（范围/验收变更）后任务回到待投喂。调整说明与关联关系随看板状态与反馈记录（feedback.md）落盘；重试后再次连续失败 3 次仍挂起（与 FR-04 异常处理口径一致）。
- **异常处理**：版本合并冲突（多人同时改）一期不做自动处理，依赖占用提示（规则 7）降低风险；看板数据损坏时从资产文件重建。

#### 3.3.8 FR-08 生态工具协同（V1.2 新增）

- **功能描述**：将与开发工作流相关的外部工具纳入项目工作流**并行使用**——本产品不集成其代码/API，而是通过"产物格式对齐 + 提示词使用指引 + 工具登记反馈"三层机制协同，覆盖 SDD 工具链与 MCP 工具生态（清单见附录 F）。
- **输入**：用户在协同工具注册表中的启用配置；各流水线产出物。
- **输出**：适配格式的产物导出；内嵌工具指引的提示词（经 FR-04）；工具使用反馈记录。
- **业务规则**：
  1. **协同工具注册表**：项目级配置文件登记可用工具（名称/类别/启用状态/说明），提供默认清单（附录 F），用户可增删改；
  2. **产物格式适配**：FR-01 需求文档与 FR-04 任务清单/提示词支持按目标工具格式导出——Spec Kit 兼容（spec.md/plan.md/tasks.md 结构）、Taskmaster 兼容（PRD 纯文本 + tasks.json 结构）、通用 Markdown；导出时保留本产品内原件不变；
  3. **提示词内嵌指引**：按 FR-04 规则 8，提示词可内嵌协同工具使用指引（纯文本建议），用户可在预览时删除；
  4. **并行不依赖（CON-13）**：任何协同工具缺失/不可用不阻断本产品任何主流程；
  5. **反馈闭环**：工具使用效果可记录入 FR-07 反馈体系，作为注册表内启用状态的调整依据。
- **异常处理**：注册表配置损坏时回退默认清单并提示；适配导出失败时降级为通用 Markdown 导出。

## 6 数据需求

### 6.1 数据模型概述

采用文件系统存储（CON-07），无数据库。核心实体及其文件载体：

```
projects/
  └─ <项目名>/
       ├─ project.json          # 项目元信息（名称/模板/创建时间/schemaVersion/owner/工程规则引用）
       ├─ rules.md              # 项目级工程规则（自动注入 FR-04）
       ├─ tools.json            # 协同工具注册表（FR-08：工具名/类别/启用状态）
       ├─ docs/
       │    ├─ 需求/            # FR-01 流水线产出（含滚动底稿、阶段记录与最终文档）
       │    └─ 过程档案/        # 澄清记录、评审意见等
       ├─ analysis/             # FR-03 结构画像与规整报告
       ├─ pipeline/
       │    ├─ state/           # FR-06 流水线状态存档（断点索引）
       │    ├─ orchestration/   # FR-04 编排数据：编排计划、逐环输入包/输出/交接摘要（规则 9.g 全量落盘）
       │    └─ tasks.json       # FR-04 任务拆分清单（含依赖与执行状态）
       ├─ prompts/
       │    ├─ <模块>/<任务>/   # 各模块提示词（含版本子目录）
       │    └─ feedback.md      # G6 效果反馈记录
       ├─ testcases/            # FR-05 测试用例
       ├─ exports/              # FR-08 适配格式导出物（spec/tasks 等按目标工具组织）
       └─ assets/               # .drawio 图示等
```

> 注：Provider API Key 等服务端密钥**不存放于上述目录树任何位置**（G-03），经环境变量或项目树外的独立加密配置注入。

实体关系（文字描述，drawio 图见附录 B）：项目 1:N 任务单元；任务单元 1:N 提示词（版本化）；项目 1:N 流水线运行记录；提示词 1:N 执行反馈记录；项目 1:N 协同工具配置。

### 6.2 数据字典（核心数据项）

| 数据项 | 载体 | 类型 | 说明 |
|--------|------|------|------|
| 项目元信息 | project.json | JSON | 名称、模板来源、创建时间、**schemaVersion（S-03）**、**owner（一期恒为空字符串，S-06 多用户预留）**、Provider 配置引用（仅存 Provider 名称，不存 Key，G-03） |
| 工程规则 | rules.md | Markdown | 技术栈约定/编码规范/目录约定，自动注入提示词；由 FR-02 骨架初始化、FR-07 编辑维护（G-07） |
| 协同工具注册表 | tools.json | JSON | 工具名、类别（SDD/文档检索/代码智能/打包/推理）、启用状态、说明（FR-08） |

### 6.3 数据存储与备份

- 存储：全部为文件系统文本文件（Markdown/JSON/.drawio XML），UTF-8 编码；
- 备份：按 NFR-08 定期自动备份至独立备份目录（可配置外部路径/网盘同步目录）；**备份内容不含任何 API Key 明文**（G-03）；
- 保留周期：备份默认保留 30 天（可配置）；项目删除一期为"二次确认后直接移除"（S-01），恢复依赖备份；回收站机制见二期 FU-04。

## 7 验收标准

### 7.1 功能验收标准

| AC-03 | FR-03 | 提供同机有效路径后，**在验收方案冻结的基准环境与数据集下**（机型/目录样本，G-09）产出结构画像与分级规整建议，指标阈值以 POC 结论冻结后写入验收方案（G-01）；路径不存在/越界（白名单外）时被拒绝并提示 |

### 7.2 性能验收标准

| 编号 | 指标 | 验收标准 |
|------|------|----------|
| AC-08 | NFR-01/02 | localhost 单机常规操作响应 ≤ 2 秒；10 并发指标留待二期局域网化验收时启用（基准环境定义于验收方案，G-09） |
| AC-09 | NFR-08 | 触发备份后备份目录出现完整项目快照，且恢复演练可还原项目；快照中无 API Key 明文（G-03） |

### 7.3 验收流程

1. 开发方完成自测并提交验收环境（localhost 单机部署实例）；
2. 按第 7.1/7.2 节标准逐项验证，记录结果；
3. **验收范围分层口径（G-05）：P0 需求对应 AC 项全部通过为验收通过的前提；P1 需求对应 AC 项（AC-06/AC-07/AC-13）按实际交付批次验收**；
4. 未通过项回到开发修正后复验；
5. 验收结论由项目委托方确认签署。
