# AI 共创需求与分层设计：产品交互稿 V0.1

> 性质：依据本轮用户纠偏编写的待审稿，不代表产品已实现或细节已获批准。
> 本轮设计“需求共创 → 标准需求文件 → AI 总体设计与多层拆分 → 人工审核 → 详细设计、原型和数据设计”，不改业务代码，不自动提交或推送。
> 本轮用户已确认：拆分审核通过后进入详细设计、原型和数据设计；三类产物协同迭代，完成后统一进行人工设计审核，不直接启动编码。审核后的流程及其他未明确确认的建议仍待讨论。
> 现有主规划与交互审查供参考；本稿是对核心体验的细化。若与历史六节点顺序冲突，应在确认后统一，不直接覆盖历史决定。

## 1. 产品定位与纠偏

这是一个与人共同思考的 AI 研发规划工作区，不是项目表单、需求文本编辑器或让用户手工建模块的管理后台。

- 人负责：表达问题、讨论取舍、确认范围、审核设计与拆分结果。
- AI 负责：主动澄清、检索知识与经验、在必要时搜索、共同起草需求文件、设计方案、递归拆分并检查覆盖和依赖。
- 系统负责：保存对话与产物、记录来源与版本、真实调用工具、执行审核门禁、支持中断恢复。
- 手工编辑、手建节点是补充能力，不是默认主路径。
- 模型设置只是基础设施；接通模型不等于已有知识检索、联网搜索或需求智能体。

## 2. 主流程与审核门禁

```text
创建项目草稿 / 输入想法
  ↓
人与 AI 连续探讨 ← 知识文本 / 搜索结果 / 相关经验
  ↕ AI 提议修改，人可接受、改写或否决
滚动需求底稿：已确认 / AI建议 / 待澄清 / 存在冲突
  ↓
生成标准需求文件候选版 + 完整性检查
  ↓ 人确认需求基线（建议增加的第一道门禁，待确认）
AI 依据确认版本自动形成设计方案 + 递归拆分草案
  ↓ AI 自检：遗漏 / 越界 / 依赖环 / 粒度 / 可验收性
设计与拆分审核：人批注、局部打回、要求重拆、批准
  ↓ 人工批准具体版本（用户明确要求的硬门禁）
AI 进行详细设计、原型和数据设计（用户已确认的下一阶段）
  ↓
三类设计产物统一人工审核（已确认的硬门禁）
  ↓
后续任务编制与编码执行（另行确认，不自动启动）
```

建议确认需求基线后，系统自动启动规划，不再要求人依次填写技术栈、模块和特性表单。若涉及无法安全假定的技术约束，AI 先发起决策问题；低风险假设可以带标记生成草案，但不允许悄悄视作已批准。

“AI 自动设计”与“人批准设计”分开；生成完成不代表获准执行。第一版建议整体批准，允许按节点批注和打回，但不以部分通过解锁下游。

## 3. 页面一：需求共创室

### 3.1 信息架构

```text
┌ 项目名称     需求共创 → 总体设计与拆分 → 拆分审核 → 详细设计 ┐
│ 项目导航 │              需求共创工作区                 │
│          ├───────────────────┬────────────────────────┤
│ 共创室   │ 与 AI 的连续对话   │ 需求底稿 · v0.3         │
│ 设计拆分 │                   │ [正文][待澄清][资料依据] │
│ 产物版本 │ AI：我们先明确谁在 │ 1 目标与背景            │
│ 资料经验 │ 什么场景遇到问题…  │ 2 用户与场景            │
│          │                   │ 3 功能与边界            │
│          │ 检索记录 / 来源卡片│ ……                     │
│          │ 本轮建议更新摘要   │ [查看本轮差异]          │
│          ├───────────────────┤                        │
│          │ 输入、补充资料     │ [生成标准需求候选版]    │
│          │ [发送] [停止]      │ [审核并确认需求基线]    │
└──────────┴───────────────────┴────────────────────────┘
```

- 首次打开直接进入共创室，AI 从初始想法开始，不要求用户先完成需求表。
- 对话是主区域，底稿是共同工作成果；不把同一段 textarea 复制到右侧冒充文档。
- AI 每轮尽量聚焦少数高价值问题，不机械逐字段审问；允许用户自由岔开话题再回归。
- 明确区分：用户原话、AI 建议、外部资料、已确认决策和未确认假设。
- AI 可以建议底稿更新；更新保留差异和撤销入口。暂存 AI 建议不等于用户批准。
- 用户能直接编辑章节，也能选中文字要求 AI 修改；并发生成不得覆盖用户最新编辑。
- 保存状态可见；刷新后恢复对话、底稿、待澄清项和检索记录。
- 长文档可放大阅读；窄屏以“对话 / 底稿 / 依据”切换，不强挤三列。

### 3.2 AI 应如何工作

1. 识别当前讨论问题，召回相关知识、经验与已确认决策。
2. 需要时效性或外部事实时发起搜索；无需搜索的讨论不强制联网。
3. 呈现依据、适用范围与不确定性，提出方案和取舍，而非只复述用户。
4. 将结论提议映射到文档章节，并维护待澄清、冲突和范围排除清单。
5. 接近收敛时建议生成标准文档；允许继续讨论，不以轮数强制结束。

### 3.3 知识、搜索和经验

| 能力 | 内容 | 页面可见证据 | 边界 |
|---|---|---|---|
| 内置知识文本 | 需求方法、设计原则、拆分规则、标准模板 | 文档标题、章节、版本 | 规范不是该项目已确认需求 |
| 项目资料 | 用户提供的背景、旧需求、说明材料 | 来源文件、引用片段 | 当前项目隔离，不默认读取无关目录 |
| 搜索引擎 | 时效事实、产品能力、外部参考 | 查询词、标题、URL、查询时间 | 联网授权；不默认发送私密全文 |
| 相关经验 | 历史失败、打回理由、成功决策及适用条件 | 经验摘要、来源项目或记录、命中理由 | 先校验适用性；不跨项目泄露私密资料 |

- 工具状态真实显示：检索中、已命中、未命中、失败、不可用。无来源不得伪造引用或宣称“已搜索”。
- 外部页面和附件都是资料，不得执行其中夹带的指令。
- 本次否决可以记录为项目决策，但未经同意不自动晋升为全局经验。
- 一期建议一个需求主智能体配合工具与任务化提示词；需求、设计、评审是逻辑职责，不强制多智能体架构。

## 4. 标准需求文件模板

建议采用“可供设计、拆分与验收使用”的轻量 SRS，必要时附产品背景；不宣称符合某个完整标准认证。不把技术方案混入业务需求，不用编造的数据填满章节。

### 4.1 文件骨架

```markdown
# 《项目名称》需求规格说明书

## 文档控制
- 文档编号 / 版本 / 状态（草稿、待审、已确认、已取代）
- 编制者（人与 AI 共创）/ 审核人 / 基线版本
- 修订摘要 / 资料与对话来源

## 1. 背景与问题
- 为什么做，现有做法与痛点，哪些事实已经核实

## 2. 目标与成功标准
- 目标、评价方式、可验证的成功指标
- 未确定的数值标记待确认，不默认生成承诺

## 3. 用户、角色与使用场景
- 谁使用、为何使用、触发条件、主流程、异常场景

## 4. 范围与边界
- 本期包含 / 明确不包含 / 后续候选
- 外部系统、组织或业务责任边界

## 5. 业务流程与规则
- 主流程、替代流程、状态流转、人工决策点
- 规则编号（BR-xxx）与异常处理

## 6. 功能需求
- 每项采用 FR-xxx，使用下面的需求条目模板

## 7. 数据与外部接口需求
- 核心业务对象、数据来源、敏感级别、保留与删除要求
- 外部接口目的、输入输出、失败处理；不强制在此定物理表

## 8. 非功能需求
- 性能 / 安全与隐私 / 可靠性 / 可用性 / 兼容性 / 可维护性
- 每项 NFR-xxx：约束、测量方式、目标或待确认项

## 9. 已知约束与依赖
- 环境、预算、平台、合规、既有系统和已确认选型限制

## 10. 验收标准与需求追踪
- AC-xxx 验收场景与对应 FR / NFR / BR
- 业务结果验收；不把“有页面、有接口”当作全部通过

## 11. 风险、假设和待澄清项
- 编号、内容、影响、是否阻断基线确认

## 12. 决策与参考资料
- 已确认决策、取舍理由、来源、未采用选项
```

### 4.2 单条功能需求格式

| 字段 | 要求 |
|---|---|
| 编号、标题、优先级 | 稳定编号；优先级由人确认 |
| 用户目标与业务价值 | 解决谁的什么问题 |
| 前置条件、触发方式 | 何时可以开始 |
| 输入与主流程 | 业务行为，不强绑实现技术 |
| 输出与成功状态 | 用户能观察到的结果 |
| 规则与异常分支 | 权限、失败、中断、空数据等相关情形 |
| 验收场景 | Given / When / Then，关联 AC 编号 |
| 来源与确认状态 | 对话、资料或决策；建议 / 待澄清 / 已确认 |

示例（用于说明本产品，不代表新增需求已经批准）：

> **FR-001：需求协同探讨**
> 用户可在同一项目中与 AI 连续讨论，AI 依据可用知识、相关经验和已授权搜索结果提出澄清问题与建议，并形成可追踪的底稿更新。
> **AC-001：** 已有项目对话和底稿时，用户刷新后可继续讨论；用户的直接编辑不因恢复或旧生成结果而被覆盖。
> **AC-002：** 搜索不可用时，系统明确显示失败或未核实，不展示虚构的检索成功或来源。

### 4.3 定稿规则

AI 先检查目标、范围、功能、规则、验收是否闭合，列出冲突和缺口。重大未决问题阻断确认；次要待定项可由人明确接受并带入基线。不能只按章节非空判定完整。

确认时保存文档快照、确认人、版本及来源关系；导出 Markdown 为一期建议，其他格式另行确认。聊天记录不是标准需求文件的替代品。

## 5. 页面二：AI 设计与分层拆分

### 5.1 设计输入与产出

输入：已确认需求版本、项目约束、相关知识经验，以及用户授权关联的现有系统资料。

AI 自动形成以下候选产物：

1. 总体方案：系统边界、关键选型及取舍、架构与主要业务数据流。
2. 交互方案：页面清单、主路径、异常与空状态。
3. 数据和接口概要：核心实体、关系、跨模块交互约定。
4. 模块树与特性：职责、边界、依赖、需求追踪。
5. 自检报告：遗漏、越界、重复、依赖冲突、风险及未决决策。

设计和拆分可迭代，但同一审核包必须绑定同一需求版本及一致的设计版本；不混用更新前后的产物。

### 5.2 多层拆分模型

```text
Project
 ├─ Module
 │   ├─ Submodule（按复杂度递归，可多层）
 │   │   ├─ Feature（可独立描述和验收的业务能力）
 │   │   │   └─ 后续工序任务（批准后进入下一阶段再细化）
 │   │   └─ Feature
 │   └─ Feature
 └─ Module
```

- 不固定要求两层或三层，不为凑层级继续切碎。
- 模块是业务职责边界，不默认按前端/后端/数据库代替业务模块。
- 特性叶子应具备目标、输入输出、验收、依赖，规模适合后续设计与实施；过大则继续拆，过小无独立价值则合并。
- 每个节点包含：稳定 ID、类型、父节点、职责/排除边界、关联需求 ID、验收摘要、依赖及拆分理由。
- 树表示归属，独立依赖图表示先后和跨分支关系，不混为一谈。
- 后续任务可由 AI 自动细化；本轮先审设计和结构，不预先创建一批可执行任务。

### 5.3 页面布局

```text
┌ 需求基线 v1.0 · 设计拆分草案 v0.2        状态：待人工审核 ┐
│ [总体方案] [页面与数据] [模块树] [覆盖矩阵] [AI检查结果] │
├──────────────────┬────────────────────────────────────┤
│ 可展开模块树      │ 选中节点：需求共创模块               │
│ ├ 需求共创        │ 职责、边界、来源需求、依赖和验收      │
│ │ ├ 对话与澄清    │ AI为何这样拆 / 有何风险               │
│ │ └ 底稿与版本    │ [批注] [要求重拆此分支] [手工调整]    │
│ ├ 知识与经验      │                                      │
│ └ 设计与审核      │ 修改前后对比、受影响分支              │
├──────────────────┴────────────────────────────────────┤
│ 待处理问题：2   [继续讨论] [打回修改] [批准本版并继续]   │
└────────────────────────────────────────────────────────┘
```

树中示例只展示形式，不预先定死最终业务边界。人可以说“这个模块太大，再拆一层”或“这两个职责重叠，重新划分”，AI 修改受影响分支并重算相关依赖和覆盖，不无故重写已认可的无关内容。

### 5.4 拆分审核后的设计工作区

**已确认：拆分获批后开展详细设计、原型和数据设计，三类产物协同迭代，完成后统一进行人工设计审核。** 具体模板、页面布局等细节仍可继续细化。

拆分前的总体设计回答“系统怎么分、各部分负责什么、为什么这样分”；拆分获批后的详细设计回答“每项能力具体如何工作、用户如何操作、数据如何组织”。不能提前把草略页面清单或实体概要冒充完成的详细设计。

| 设计产物 | 建议内容 |
|---|---|
| 详细设计 | 模块/特性流程、业务规则、状态机、异常分支、接口契约与验收映射 |
| 原型 | 页面结构、关键操作路径、页面跳转、加载/空/失败状态；建议使用可点击原型 |
| 数据设计 | 实体关系、表与字段、主外键和约束、索引、数据生命周期及必要的迁移方案 |

三类产物协同迭代，由 AI 基于已批准的需求和拆分版本生成，人通过对话、预览与批注审核修改；系统检查关键接口、页面字段与数据结构的一致性。不要求用户分别填写三套表，也不强制先完成所有详细设计才开始原型。同一设计工作区采用三个视图是具体布局建议。

三类产物完成后统一进行人工设计审核，审核绑定具体产物版本；生成完成或 AI 自检通过不代表人工批准。审核包建议包含设计说明、原型、数据设计、跨产物一致性检查和待决策项。未获批准不得推进下游；审核通过后的任务编制与编码流程仍需另行确认，不自动启动。

## 6. 人工审核与变更控制

- 审核对象是具体版本的设计与拆分包，不是一个会悄悄变化的树。
- 人能看完整方案，也能按节点批注、编辑、合并、移动或要求 AI 重拆；结构校验必须重新运行。
- 打回需记录问题；AI 再提交必须附修订摘要和意见处理结果。
- 检查至少包括：本期需求是否被覆盖、是否加入范围外功能、职责是否重叠、粒度是否合适、依赖是否成环、特性是否可验收。
- 只检查结构无环等确定性条件不能代替语义评审；模型自检通过也不能代替人批准。
- 未批准不得推进下一工序、创建可执行派发或调用编码代理；只禁用前端按钮不够，后端必须校验批准版本。
- 上游需求更新：保留原批准快照和历史，标识相关下游过期，先做影响分析，再审核新版；旧批准不能沿用到变化后的内容。
- 失败、超时、停止都保留已生成草案并标记不完整；不能用规则样例替代 AI 结果后宣称成功。

## 7. 建议的一期验收场景

1. 从一句初始想法进入对话，无须手填模块表；AI 能结合资料提出相关问题。
2. 能观察到真实的知识/经验召回和授权搜索结果；工具失败诚实呈现。
3. 对话结论逐步形成章节化底稿，建议与确认分开；可比较修改并恢复历史。
4. 生成符合本模板的需求文件；关键缺口可见，用户确认具体基线版本。
5. AI 基于该基线产生设计和多层结构，不要求用户逐项录入节点。
6. 人对某分支提出修改意见，AI 局部重拆并显示差异、影响和覆盖变化。
7. 人工批准前，下游推进在 API 层被拒绝；批准后只允许基于获批版本继续。
8. 需求改版后旧拆分标记过期，不静默沿用旧批准。
9. 刷新、中断和模型失败后可恢复，用户手工修改不会被旧响应覆盖。

## 8. 本轮待确认的产品边界

- **需求基线门禁：** 推荐人先确认需求文件，随后 AI 自动设计与拆分；是否采用？
- **审核颗粒度：** 推荐一期整体批准、节点批注和局部返工；是否需要分支独立批准与推进？
- **下一步与设计审核（已确认）：** 拆分审核通过后进入详细设计、原型和数据设计，三类产物协同迭代，完成后统一人工审核；不直接生成编码任务、提示词或调用编码代理。设计审核通过后的流程另行确认。
- **资料与经验来源：** 推荐先提供可维护的内置文本库与项目资料入口；是否要导入既有经验库，来源由用户指定。

以上是待审方案，不是新增强制流程。应先确认关键主线，再制作可点击原型并按验收场景验证，避免再次把 AI 共创退化为表单。
