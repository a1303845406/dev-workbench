# 开发工作台 · 交互原型说明 V1.5

## 1 定位

本原型是基于 SRS V1.2.2 的**设计评审材料**，不是可运行产品、不是后端实现、不是 POC，也不会调用 Provider、扫描真实目录、写入项目文件或修改源码。

打开 `开发工作台-交互原型-V1.0.html` 即可离线浏览。原型使用原生 HTML/CSS/JavaScript 和内存示例数据，无 CDN、无外部网络依赖。

## 2 已覆盖的关键旅程

## 3 评审重点

1. 主流程是否从创建项目连贯到需求、规整、提示词、测试、看板和资产归档；
2. 哪些状态必须用户确认，哪些动作只能产出方案而不自动修改源文件；
3. FR-04 的四层输入包、预算单位（tokens）与交接摘要 stale 语义是否清晰；
4. 外发范围确认、脱敏门、硬约束包和项目规则冲突提示是否足够可见；
5. S5 两段冻结、S7 严重问题裁决以及中断/挂起恢复是否符合工作习惯；
6. 页面 IA、信息密度、字段名与中文文案。

## 4 已知限制

- 所有模型输出、扫描结果、文件列表和版本差异均为静态示例；
- 不验证真实浏览器布局、不验证 Clipboard/Firefox/Edge 兼容性；
- 不验证 AOCI-CODE、tree-sitter、Provider、drawio viewer 或任何外部工具；
- 原型中的“确认”“执行下一环”“创建项目”等均只改变页面内存；刷新页面会恢复初始示例。

## 5 不应从原型推断的内容

原型不等于产品已经选定 Vue、FastAPI 或 Element Plus；这些是总体设计中的建议选型，需用户/技术评审后才进入开发计划。原型也不改变 SRS 的分期边界，二期局域网 HTTPS、鉴权、代码切片注入、Git 深度集成等不在本轮开发范围。

## 7 V1.2 调整记录（按用户使用反馈）

| 用户疑问 | V1.2 落点 |
|---|---|
| ① 「进入工作台」直接落在需求页，需求探索应是项目内第一阶段 | 新增「工作台」落地页（项目内第一入口）：四阶段卡片（① 需求探索 → ② 项目规整 → ③ 提示词工程 → ④ 测试与交付）各带状态与进度，从工作台按序进入；需求探索明确标注为项目第一阶段 |
| ② 扫描结果希望有图示化呈现（类 Jarvis 页面） | 项目规整扫描后新增「结构图示」页签：SVG 环形目录图（中心=项目，节点=目录，颜色=健康度，含文件量与图例），可切换回「清单视图」；正式产品由扫描结果生成并支持下钻联动 |
| ③ 模块组合应是模型按任务自动建议、人来决策，而非全局预设 | ②模块组合 步骤重构：输入任务描述（参考档位仅作先验）→「按任务自动组合」逐任务给出模块建议与理由 → 人在建议上增删（标记已人工调整）→ 逐任务硬约束校验后进入拆分；删除了三档预设一键覆盖组合的交互 |
| ④ 提示词工程应体现提示词管理（不同阶段） | 第 06 步改为「提示词管理」：全环/全阶段管理表（环·阶段 / 任务 / 状态 / 版本 / 交接摘要 / 操作），点击查看载入下方编辑·渲染双页签与定稿门操作；版本对比回滚仍归「资产与版本」 |
| ⑤ 任务看板与资产分别是什么 | 两页顶部各加定位说明卡：任务看板=外部 IDE 执行状态跟踪板（待投喂→已投喂→已完成/失败，失败须记录返工原因），回答「交出去之后执行得怎么样」；资产与版本=规划产出档案库（需求文档、提示词版本、用例、导出物，版本只增不改），回答「沉淀了什么、能否追溯」；工作台页也有同样的一句导引 |

| ③ 看板任务失败后能否动态调整任务？（需求有无描述） | 原型已加闭环：失败卡片提供「重新拆分」（按失败原因细化为两个子任务进入待投喂，原任务留档标记"已细化拆分"）与「调整范围后重试」（填写调整说明，回到待投喂并记入反馈）。**SRS V1.2.2 现状**：FR-04.e/FR-06 覆盖"环失败挂起+断点恢复"、FR-07 规则 3 仅"记录返工原因"、FR-04 规则 9.f 的自动拆分发生在编排前——**"看板失败→动态重拆分/调整范围"的闭环未被描述**，原型作为评审提案呈现；若采纳需按变更流程补入 SRS（含失败任务与新子任务的追溯关系、重试计数语义） |
